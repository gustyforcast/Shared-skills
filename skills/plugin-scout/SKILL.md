# Plugin Scout

Recommend plugins grounded in authorised evidence rather than imagined needs.

## Inspect

1. Identify the projects, task history, documents or repositories the current host can access. Read only the minimum authorised material necessary.
2. Inventory relevant existing skills and capabilities. Separate a real gap from a duplicate or a temporary inconvenience.
3. Find repeated manual steps, recurring failures, predictable checks, hand-offs or prompts that needed the same corrections. Require two independent occurrences or one clearly durable, substantial workflow.
4. For each candidate select the smallest implementation: skill-only guidance, skill plus deterministic script, skill plus a genuinely available external connector, or a consolidation/update to existing skills.
5. Compare value, recurrence, risk reduction, portability, determinism and testability. Reject unsupported demand claims, hidden private context and unqualified dependencies.

## Output

Return up to five ranked candidates. Each must identify: observed evidence and source scope; exact trigger; outcome and benefit; overlapping skills; intended audience; required runtime and permissions; smallest workable test; possible negative scenarios; and a proposed skill/plugin structure. Include rejected near-misses with reasons. If there is no credible candidate, say so.

## Boundaries

Scouting is **read-only**. Do not scaffold, install, change other skills, copy credentials, alter accounts, or publish without explicit approval. Do not assume a particular user's workstation, organisation, software or chat history exists in another environment. When the host cannot inspect previous tasks, clearly describe the evidence gap instead of pretending the review was exhaustive.
